Lakukan AUDIT READ-ONLY (jangan edit/tulis file apapun dulu, ini murni analisis + laporan) terhadap seluruh pipeline eksekusi Ruko sebagai persiapan sebelum npm publish. Guardian LLM (Roadmap #5) sudah selesai dan ter-commit — audit ini mengecek apakah semua bagian lain sistem sudah aman untuk dipakai publik, bukan cuma approval-gate.

CAKUPAN AUDIT
1. executor.ts — bagaimana command benar-benar dieksekusi setelah lolos approval gate + guardian LLM. Apakah ada jalur yang BYPASS kedua lapisan itu sama sekali (tool internal tertentu yang langsung exec tanpa lewat detectRisk/guardian dulu)?
2. tools.ts — untuk SETIAP tool (read_file, write_file, edit_file, exec, glob, code_search): apakah bisa dipakai untuk keluar dari working directory project (path traversal ke luar folder kerja, misal ../../../etc/passwd)? Termasuk tool read-only (glob/code_search) — apakah bisa baca file sensitif di luar scope project (SSH keys, .env di direktori lain)?
3. write_file/edit_file — apakah ada validasi path sebelum menulis? Bisa overwrite file sistem (~/.bashrc, /etc/hosts) kalau diarahkan untuk itu?
4. Config loading (.ruko/config.json) — apakah ada validasi terhadap isi config yang dimuat? Kalau file config dimanipulasi pihak lain (bukan lewat wizard resmi), bisa menyuntik command berbahaya lewat field config?
5. Guardian LLM — cek implementasi yang baru selesai:
   a. Apakah fail-safe-nya (network error/timeout → fallback ke tanya user, bukan auto-allow) benar-benar teruji, bukan cuma diklaim di desain?
   b. Verifikasi apakah 3 keputusan desain berikut BENAR-BENAR terimplementasi:
      - Verdict "safe" → auto-allow TAPI menampilkan indikator singkat alasan (mis. "✓ Guardian: aman — <reasoning>") sebelum eksekusi, bukan diam-diam.
      - Ada opsi config guardianProvider/guardianModel (opsional) untuk mengarahkan guardian ke model berbeda dari chat utama.
      - Verdict guardian dicatat ke file audit log terpisah (misal .ruko/guardian-audit.log: timestamp, command, verdict, reasoning) — BUKAN masuk context chat utama.
      Kalau salah satu TIDAK ada, laporkan sebagai gap yang perlu ditambahkan (jangan langsung diimplementasi di sesi audit ini).
   c. Apakah ada celah guardian dipanggil dengan command kosong/malformed yang bisa bikin dia crash atau salah verdict?
6. Dependency check — jalankan npm audit, laporkan dependency dengan known vulnerability yang perlu di-patch.
7. Exposed secrets/hardcoded default — audit lebih luas dari sekadar API key: apakah ada URL internal, path spesifik developer, atau default lain yang tidak seharusnya ada di kode publik.

OUTPUT
Laporan di chat (JANGAN tulis ke file dulu): daftar temuan dengan severity (HIGH/MEDIUM/LOW/INFO), file:baris, rekomendasi. Kelompokkan mana yang WAJIB diperbaiki sebelum publish vs yang bisa jadi known limitation/roadmap.
Setelah laporan ini saya review, baru kita putuskan mana yang perlu ditindaklanjuti — jangan langsung implementasi apapun di sesi ini.

Jawaban untuk 3 pertanyaan: 1. Auto-allow untuk
  verdict "safe": SETUJU auto-allow tanpa y/N
  manual (sesuai desain awal, biar reduce
  friction beneran kerasa) — TAPI tampilkan
  indikator singkat kenapa (mis. "✓ Guardian:
  aman — <reasoning 1 kalimat>") sebelum
  eksekusi, bukan cuma langsung jalan diam-diam.
  Ini biar ada jejak yang kelihatan real-time
  kalau nanti perlu ditelusuri. 2. Provider LLM
  guardian: pakai provider yang sama untuk
  sekarang (sesuai codebase single-provider),
  TAPI tambahkan opsi config terpisah
  (guardianProvider/guardianModel) yang opsional
  — kalau nanti user pakai model lemah (flash)
  untuk chat utama, guardian bisa diarahkan ke
  model yang lebih kuat secara terpisah tanpa
  refactor besar. 3. Logging verdict: WAJIB
  dicatat ke audit log terpisah (bukan masuk
  context chat utama, biar nggak bikin bingung
  riwayat percakapan) — simpan ke file log (mis.
  .ruko/guardian-audit.log) berisi timestamp,
  command, verdict, reasoning. Ini penting untuk
  audit trail kalau nanti ada masalah yang perlu
  ditelusuri balik. Setuju lanjut ke implementasi
  (M2) dengan jawaban di atas.
