Implementasikan Roadmap #5 — "Approval pintar (guardian LLM)" — untuk menutup 6 known limitation yang tercatat di PROGRESS.md dari audit keamanan sebelumnya (v0.7.1-v0.7.2): semantic analysis payload interpreter, variable indirection, eval/subshell obfuscation, quote-aware chain splitting.

KONTEKS
Approval gate saat ini (src/core/approval.ts) berbasis regex/pattern matching terhadap command mentah. Ini sudah diaudit 2x dan menutup celah pattern-level (path sistem, chaining, redirect disk, base64|sh, interpreter inline flag). Tapi regex punya batas fundamental: dia tidak bisa memahami MAKNA command, cuma cocokin string. Contoh yang masih lolos:
- python3 -c "shutil.rmtree('/etc')" — sudah DANGEROUS (dari fix sebelumnya, karena ada flag -c), tapi levelnya sama untuk semua isi python -c, termasuk yang aman ("print('hello')")
- Variable indirection: X=/etc; rm -rf $X — regex tidak bisa resolve nilai variabel
- Command dalam base64/hex/rot13 yang di-decode runtime

TUJUAN: GUARDIAN LLM SEBAGAI LAPISAN KEDUA
Bukan mengganti regex yang sudah ada — regex tetap jalan sebagai filter cepat pertama (murah, deterministik). Guardian LLM jadi lapisan KEDUA yang dipanggil khusus untuk kasus yang regex sendiri sudah ragu (level DANGEROUS atau ada pola interpreter-inline/encoding terdeteksi), bukan untuk setiap command.

DESAIN YANG DIMINTA
1. Tambah fungsi baru assessWithGuardian(command: string): Promise<{verdict: 'safe'|'dangerous'|'blocked', reasoning: string}> di approval.ts.
2. Guardian dipanggil HANYA ketika regex level saat ini sudah DANGEROUS (bukan untuk command yang sudah pasti BLOCKED oleh regex — itu tidak perlu ditanya lagi, dan bukan untuk yang sudah pasti NONE aman berdasarkan regex, supaya tidak boros memanggil LLM untuk command remeh seperti "ls" atau "git status").
3. Prompt untuk guardian harus singkat, fokus: minta LLM menilai APAKAH command ini, kalau dieksekusi, akan menghasilkan efek destruktif setara file-system wipe/system damage — bukan minta dia menjelaskan command secara umum. Sertakan instruksi eksplisit: kalau ragu, pilih 'blocked' (fail-safe), jangan 'safe'.
4. PENTING — LOOP PREVENTION: guardian LLM ini boleh memanggil provider LLM yang SAMA dengan yang dipakai user untuk chat utama, TAPI harus pakai call terpisah dengan max_tokens kecil (cukup untuk verdict singkat + alasan 1 kalimat) dan TIDAK boleh masuk ke context/history percakapan utama. Pastikan ini tidak menciptakan rekursi kalau user sedang menyuruh Ruko sendiri mengedit approval.ts atau menjalankan command yang memicu guardian terhadap dirinya sendiri.
5. Kalau pemanggilan guardian gagal (network error, rate limit, dll): DEFAULT ke perilaku fail-safe — anggap sebagai 'blocked' atau minimal tetap 'dangerous' (minta approval manual), JANGAN auto-allow hanya karena guardian tidak bisa dihubungi.
6. Tambahkan opsi config: guardianEnabled?: boolean (default true), guardianTimeoutMs (default wajar, misal 5000) — kalau timeout, fallback ke fail-safe seperti poin 5.
7. UI: saat guardian sedang dipanggil, tampilkan indikator singkat ("Memeriksa keamanan command...") memakai mesin redraw bersama yang sudah ada (LineEditor) — JANGAN buat jalur render baru.

VERIFIKASI WAJIB
8. Test dengan skenario dari 6 known limitation di atas — pastikan guardian menangkap SEMUA contoh yang sebelumnya lolos (python -c dengan payload destruktif, variable indirection, eval obfuscation).
9. Test negatif: pastikan command aman yang REGEX-nya sudah DANGEROUS tapi sebenarnya tidak berbahaya (contoh: python3 -c "print(1+1)") tetap bisa lolos guardian sebagai 'safe' — supaya tool tidak jadi terlalu paranoid dan minta approval untuk semua pemakaian interpreter.
10. Test fallback: simulasikan guardian call gagal/timeout, pastikan behaviour fail-safe berjalan (bukan auto-allow).
11. Update PROGRESS.md: tutup 6 known limitation ini, tapi TETAP catat batasan baru guardian LLM itu sendiri kalau ada (misal: guardian bisa salah nilai kalau LLM-nya sendiri di-prompt-inject lewat command yang aneh — laporkan kalau ini kamu nilai sebagai risiko nyata atau bukan).

JANGAN mulai coding sebelum konfirmasi dulu ke saya: apakah desain "regex dulu, guardian LLM cuma untuk kasus DANGEROUS" ini masuk akal, atau ada trade-off yang menurutmu perlu didiskusikan dulu (biaya API call tambahan tiap command mencurigakan, latency, dll).
